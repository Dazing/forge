# Repository instructions

## Scope and project

These instructions apply throughout the repository unless a more specific `AGENTS.md` applies. This is a TypeScript ESM runner whose ticket backlog is a private GitHub repository: locally authored Markdown tickets are submitted as issues on a private Project v2 board whose Status field owns ticket lifecycle, and the runner executes them in fresh retained Git workspaces using Sandcastle, Pi or oh-my-pi, publishing draft pull requests to GitHub and Azure DevOps target repositories in one invocation.

## Architecture and ownership

`factory/main.ts` is the runner composition root: CLI/configuration, repository-root resolution, the provider registry built from the configured target credentials, the backlog transport built from `FORGE_BACKLOG_*` (awaited, because constructing it resolves the configured Project URL), `PublicationLedger.open`, `BacklogWorkflow` construction, the invocation logger, sandbox preflight, backlog/board validation, and invocation of `processTickets`. `factory/tickets-main.ts` is the separate submission host behind `npm run tickets`. Polling state and ticket settlement belong to the workflow, not the host.

The eight flat features under `factory/features/` own:

| Feature | Responsibility |
|---|---|
| `tickets` | Declared identity/dependencies, full-source and authored-requirements fingerprints, authored issue-body validation through `IssueIdentity`, and the six `BACKLOG_STATUSES` |
| `ticket-processing` | Backlog discovery and board-status scheduling, invocation graph/group state, global job leases, complete retries, dependency baselines, integration finalization, reconciliation, the durable `PublicationLedger`, `BacklogWorkflow` board settlement, authorization guards, credential-lapse preservation, and settlement |
| `submit-tickets` | Idempotent local-to-backlog submission: source discovery, privacy gates, plan/report, and the per-ticket issue and board effects |
| `plan-tickets` | Exact delivery-group selection, feature-owned handoff schema, and factory immutability |
| `implement-ticket` | Ticket/dependency input, three single-iteration work runs, handoff message contract, and completion enforcement |
| `review-ticket` | Single-ticket review loop, handoff message contract, and completion enforcement |
| `integrate-tickets` | Conflict-resolution/combined-review loop, handoff conflict dispositions, and no-commit completion contract |
| `publish-pull-request` | Read-only grouped PR content, gates, safe create/extension push, provider publication/update, and returned facts |

- Enter another feature only through its narrow `index.ts`, including type-only imports. Same-feature helpers and tests may use their own internals.
- `ticket-processing` may call public ticket and stage APIs. Stage features must not import each other or the coordinator, even through public APIs. `tickets` must not import processing or stages.
- `submit-tickets` enters `tickets` only through its `index.ts` and never touches the runner host, `ticket-processing`, or a stage feature; `tickets-main.ts` obeys the same boundary.
- Features must not import `main.ts`, `tickets-main.ts`, or CLI code.
- Keep stage inputs small and stage-owned. Do not expose coordinator-private attempt/workspace types or introduce a generic pipeline context.
- Keep scheduling as a coordinator-owned bounded ready queue. Do not add a mediator, event bus, stage registry, distributed state, partial-attempt recovery, multiple-process coordination, or new cancellation semantics.

`factory/infrastructure/` owns mechanisms:

- `agent-runtime/`: configured execution, agent/harness construction including model-id selection from the workspace-root `models.json` catalog (exactly one model id; ambiguous or malformed catalogs fail construction), generic feature-supplied handoff transport, MCP guidance, safe stream adaptation, generic log wiring, and the runtime `skills/` catalog. It must not own the model catalog, keep a built-in model constant, or know ticket types, planner schemas, or stage prompts. Stages choose prompts, handoff descriptions/schemas/validators, arguments, and iteration limits.
- `sandbox/`: sandbox setup/preflight, isolated per-run handoff mounts, `Dockerfile`, `check-mcp.mjs`, and the empty `masked.env` credential overlay. Preserve repository-root-based asset resolution, resolving the model catalog from the workspace-root `models.json`; directory depth must not redirect mounts. Use host networking and mount skills/models read-only at the selected harness's native global configuration paths.
- `git-provider/`: the provider registry (`GITHUB_TOKEN`, `AZURE_DEVOPS_PAT`) and its adapters, provider-neutral create/read/update contracts, browser-facing branch links, and Git subprocess operations as one unit. Do not split Git code merely for symmetry.
- `github-backlog/`: the private GitHub issue and Project v2 transport — local parsing of a pasted Project v2 URL into owner kind, owner, and project number, one read-only lookup that resolves it to the Project node id when the transport is constructed (configuration validation precedes the lookup, and the supplied browser URL is never fetched), privacy validation, issue reads/writes with revision-conflict checks, append-only comments, closure as completed, bulk board reads, and single status writes, with structured credential-redacted failures. It owns no lifecycle policy.
  Project status mutations must declare the single-select option variable as `String!`, not `ID!`; project, item, and field variables remain `ID!`. Keep schema-executed transport coverage for claim and blocked transitions so mocked HTTP success cannot hide GraphQL input-type errors.
- `logging/`: invocation logs and agent log paths.

Infrastructure must not import features, host, or CLI. Construct the provider registry, backlog transport, ledger, workflow, logger, and configured runtime once in the composition root and pass dependencies explicitly.

`factory/shared/` contains pure utilities and generic path checks only, including secret redaction. It must not import features, infrastructure, host, or CLI. Do not move invocation state or feature policy there. Reject unresolved imports and circular dependencies; `.dependency-cruiser.cjs` enforces the import graph.

## Behavioral contracts

Preserve these unless explicitly changing the corresponding behavior:

- Human-readable stage logs include concise summaries for every Pi-compatible `tool_execution_start`, regardless of native, lowercase, or MCP tool name. Raw stream events, tool output, and thinking blocks remain omitted. `submit_handoff` summaries must never include its arguments.
- Every planner, implementation, review, integration, and pull-request-content run receives one tool named `submit_handoff` whose description and strict JSON Schema come from the owning feature. Infrastructure may transport and revalidate the generic payload but must not own a union or registry of stage schemas.
- Each run uses a unique nonce-bearing control channel outside the repository: mount the contract read-only and only that run's result directory writable. The first valid handoff is atomically immutable; invalid arguments may be corrected in the same agent turn; stale, duplicate, malformed, oversized, or wrong-tool envelopes fail safely; cleanup runs after success and failure.
- Assistant prose has no completion authority. A missing accepted handoff is incomplete. Implementation, review, and integration retry only `MissingAgentHandoffError` within their three-run loops; host validation, transport, infrastructure, and accepted-handoff postcondition failures are immediate.
- A terminal assistant `message_end` with `stopReason: "error"` is an infrastructure failure even when the harness exits `0`. Preserve its `errorMessage` in the transcript and raise it before consuming a handoff; do not downgrade a failed model request to a retryable missing handoff.
- `--help` returns before `.env` loading, credentials, logging, sandbox preflight, and any network call, for both CLIs. Preserve CLI flags/defaults.
- Configure each target provider through its credential variable — GitHub uses `GITHUB_TOKEN`, Azure DevOps uses `AZURE_DEVOPS_PAT`, at least one must be present, and each ticket's declared canonical SSH URL selects its adapter, so one invocation serves mixed-provider work. Provider adapters own canonical SSH URL validation and browser-facing branch links. Clone/push use SSH; REST credentials are for publication only.
- Preserve provider request/authentication details and structured `CommandFailedError` diagnostics. Azure DevOps uses API version `7.1`, encoded URL segments, fully qualified branch refs, draft status, and a browser-facing PR URL. Redact raw credentials and Azure's derived Basic value in diagnostics, including the backlog token in every ticket comment and `main.log` record; never expose them to agents or Git arguments.
- Factory-checkout sandboxes must shadow the repository-root `.env` with the empty read-only overlay; never remove or rewrite the host credential file. Do not mask ticket repositories' application configuration.
- The private GitHub backlog is the runner's only ticket source and the Project board is the sole lifecycle authority: the runner discovers open issues with board entries, claims `In progress`, publishes to `In review`, settles merged work to `Done` (closed as completed), parks non-runnable or unauthorized work as `Blocked`, and never rewrites an authored issue body. Every runner write is one append-only comment marked with a runner operation key, idempotent across restarts. Both the backlog repository and the Project must be private, validated before any write. Configure the board with `FORGE_BACKLOG_PROJECT_URL` — the pasted `https://github.com/orgs/<owner>/projects/<number>` or `https://github.com/users/<owner>/projects/<number>` address, optionally `…/views/<number>` — never a node id: the transport parses the URL, resolves it once at construction, and keeps `GitHubBacklog.projectId`, board mutations, and sidecars node-id based. An unparseable URL, a missing URL, and an inaccessible Project are configuration failures raised before any write.
- `npm run tickets` (`factory/tickets-main.ts`) publishes authored Markdown into the backlog idempotently per ticket ID: create → board item `Backlog` → `Ready`; changed authored content updates the body; unchanged content is a no-op. Both privacy gates run before any write, `--project <url>` overrides the configured Project URL before that resolution, `--dry-run` writes nothing, and the exit codes are `0` all succeeded, `1` any ticket failed, `2` usage/configuration/lock/privacy failure.
- Submission directory inputs are non-recursive. A directory with no top-level Markdown tickets must fail with exit code `2`, name the directory, and explain how to select the ticket subdirectory or a quoted recursive glob; it must never return successful zero totals.
- Every stage dispatch, integration run, push, and provider write re-reads the issue, its board entry, and its authored requirements hash through a coordinator-supplied authorization guard. A closed issue, a status the runner did not claim (a published member's expected status is `In review`, resolved when the guard runs), or changed requirements raises `AuthorizationWithdrawnError`, which stage loops never swallow: the branch is pushed, the workspace retained, a preservation comment posted, and no board status written. A credential lapse detected in a stage failure report preserves the branch the same way and parks the issue as `Blocked`.
- Publication settlement is durable in the gitignored `.factory-state/`: one intent before the push, one result after the provider write, and one record per issue-and-effect, each written as a temp file plus atomic rename. Startup replays unfinished settlements, retires publications whose tracked pull request is absent or closed (returning those issues to `Ready`), and reconciles merged publications before scheduling. No path publishes a branch that already carries a draft; a retired publication stays blocked for operator reconciliation until the process restarts.
- Ticket IDs are explicitly declared stable identities, one open issue per ID; preserve the full-source `sourceHash`, the authored-content `requirementsHash` (annotation-only history never changes it), dependency metadata, front matter, slug/title derivation, and default base branch. Duplicate open IDs block both issues.
- Graph/checkpoint state is invocation-memory only; publication and settlement facts are durable in the ledger. Component IDs are retained as membership changes. Prior lifecycle evidence blocks affected work for operator reconciliation; unrelated fresh groups continue. Record each newly discovered or changed scheduling block in `main.log` and stderr with provider credentials redacted before planner selection.
- Sleep 10 seconds when no active tickets remain or when the active queue has no runnable delivery group, then rediscover tickets. Empty planner selections and retryable runnable work add no planner/retry backoff.
- Planning uses the configured harness and selects at most one exact supplied delivery group through `submit_handoff`. Reject unknown groups, changed membership/order/titles, duplicates, excess, missing handoffs, or factory mutations. Only an accepted `{ groups: [] }` is an empty selection.
- `--max-parallel` defaults to `1` and limits every agent job through one invocation lease pool. `--ticket-attempts-per-cycle` defaults to `3`; complete retries use fresh retained workspaces and reset next cycle without a lifetime cap.
- Attempts start at a validated canonical base, one-parent review checkpoint, reviewed multi-parent integration checkpoint, or verified refreshed merged base. Preserve origin, branch/SHA/cleanliness checks, sibling isolation, pinned cycle baselines, and retained failed workspaces.
- Preserve order inside an attempt: reserve → claim comment → dependency-based workspace → implementation → implementation checkpoint/trace → review → review checkpoint/trace. Publication occurs only after group runnable work settles and reviewed candidates are integrated.
- Agents never commit. Implementation/review retain their three single-iteration loops. Integration also permits three single-iteration repair runs, may enter with pending merges, must resolve all entries and document every conflict, and must leave HEAD/branch unchanged. The coordinator alone creates and validates multi-parent integration commits.
- Each successful mutating stage produces exactly one checkpoint commit. Preserve the checkpoint contract: recheck the expected branch and the HEAD captured at stage entry, require no unmerged porcelain entries, `git add --all` without force-adding ignored files, compute `Factory-Changes` from the staged tree, append the runner-owned trailers (`Factory-Ticket`, `Factory-Attempt`, `Factory-Stage`, `Factory-Outcome`, `Factory-Changes`, `Factory-Agent-Log`), reject provider credential material (including Azure's derived Basic value) before writing the message, commit with `--allow-empty` as argv and the command-local `Factory Runner <factory-runner@localhost>` identity, then require exactly one new single-parent commit whose parent is the captured HEAD, on the expected branch, with a completely clean index/worktree including untracked files. Return `{ parentSha, checkpointSha, changes }` and advance only after the postconditions.
- After hooks run, compare the checkpoint's actual tree-change outcome against its recorded `Factory-Changes` trailer. A mismatch fails the checkpoint and retains the commit without reset, amendment, or retry.
- An empty checkpoint is required when a successful stage changes no files, and its message states that outcome. Failed/incomplete stages get no checkpoint: retain the dirty workspace and the last successful checkpoint, and never reset, clean, amend, rebase, or continue that workspace. A checkpoint failure is reported as `implementation commit` or `review commit`; checkpoint trace/annotation failure is a distinct durable boundary that stops the attempt, blocks reuse for reconciliation, and never repeats the commit. Preserve the original `CommandFailedError` when checkpoint commands fail.
- Each checkpoint writes one `main.log` trace record (parent SHA, checkpoint SHA, changes, agent-log reference). The agent-log value is the invocation-relative transcript path, the identical value carried by the `Factory-Agent-Log` trailer, never an absolute `.logs` path.
- One invocation owns one instance directory `.logs/<utc-stamp>-<6-hex>/` with `main.log` at its root. Planner cycles are numbered files under `planner/` (`planner/001.log`); each attempt ID binds one timestamped directory `<utc-stamp>-<attempt-id>/` holding numbered stage files (`implement-1.log`, `review-1.log`, `integrate-1.log`, `pull-request-1.log`). Every allocation consumes the next number, including runs that fail, so a retry never overwrites a prior transcript, and all runs of one attempt ID share one directory.
- Stages pass a validated `LogTarget` (sequence directory and cycle, or attempt ID and stage) to the runtime and propagate only the reference the runtime returns; nothing reconstructs a basename, and the logging feature never parses feature-owned stage strings. Unsafe segments (empty, `..`, separators, control characters) fail before any directory is created.
- Review success requires a clean index/worktree, including untracked files, enforced at the checkpoint. PR content generation must not change HEAD or porcelain status; record its success at the workspace SHA it started from immediately after immutability validation and before publication checks or remote operations. A content trace-write failure is a `pull-request content` failure before push/provider HTTP. A branch with no commits ahead cannot publish, and the net tree diff between `origin/<baseBranch>` and HEAD must be nonempty, so checkpoint-only history cannot publish.
- Publication returns final SHA, provider-neutral PR data, persisted merge-method preference, head branch, and exact published title/body for safe extension tracking—not a terminal ticket outcome. Preserve failure substages: `pull-request content`, `commit count`, `change set`, `final SHA`, `push`, and `draft pull request`. The coordinator alone owns publication facts and included-ticket settlement.
- Squash-on-merge is a preference, never permission to merge: pull requests stay draft, no auto-complete, no policy bypass, no source-branch deletion, no repository-settings rewrite, and no local squash. Azure DevOps create requests carry `completionOptions` with `mergeStrategy: "squash"`, `isDraft: true`, `deleteSourceBranch: false`, and `bypassPolicy: false`, with no `autoCompleteSetBy` and no deprecated `squashMerge`; validate the returned draft state and persisted strategy, using one read-back GET when the create response omits it, and treat absence, non-draft, or a mismatched strategy as a structured draft-publication failure that records the created PR URL. GitHub's REST API has no per-PR merge-method field: create the draft normally, report `unsupported`, append a short runner-owned PR-body note requesting squash merge within the existing 5000-character body limit, and record the limitation in the completion annotation. Never use GraphQL auto-merge, ready-to-merge, a merge endpoint, or repository settings.
- Azure read-back must succeed at HTTP level and match the created PR ID, draft state, and requested squash strategy. Keep validation reasons and the known browser-facing created PR URL in structured command diagnostics consumed by settlement, including read-back transport and malformed-response failures; redact raw and derived credentials.
- Complete-attempt failures remain retryable and park the issue as `Blocked` with one keyed failure comment; blocked descendants are not attempted and are reported onto their own issues. Durable checkpoint/trace ambiguity blocks reuse for reconciliation. Invalid metadata still receives guarded terminal settlement.
- Record the publication intent before the push and the result after the provider write, then settle every included issue with its publication comment and `In review`; settlement failures never republish. Later reviewed descendants may extend an unchanged tracked draft.
- Publication intents carry the exact final head/SHA/title/body before push. Recover unmatched intents by reading the remote identity, adopting exact matches without another provider write and blocking ambiguity. Reconcile only the latest result per provider/repository/PR; retire all revisions together. Restore verified published baselines for restarted descendants and exclude verified merged prerequisites from new publication membership.
- Claim effects require an authoritative open/requirements/status reread before comment and status writes; never restore withdrawn claims during recovery. Preserve human status on later polls until explicit Ready re-queue. Preservation may create a separate runner-owned commit for conflict-free unfinished work, never a success checkpoint; report capture completeness separately from push success and retain unresolved conflicts locally.
- Aggregate backlog and target credentials at composition for every rejection/redaction boundary. Isolate invalid dependency chains and ordinary publication failures so unrelated delivery groups continue. Submission sidecars must match destination and complete issue identity; exact-source recovery repairs only missing effects without demoting later lifecycle states.
- Provider extension requires exact repository/number/base/head/source SHA/title/body/draft/squash identity and a reviewed descendant. Push non-force, reread after uncertain updates, and use a fresh draft when identity is missing, closed, non-draft, or externally changed.
- Before scheduling and publication, reconcile tracked merged PRs using provider merge-result identity, refreshed-base reachability, and exact published-delta application/tree comparison. Verified included IDs are satisfied by the refreshed base and settle to `Done` with closure; inconclusive evidence blocks affected descendants without replaying retained history.

## Editing and verification

- Use existing patterns and narrow public contracts. Trace consumers before changing exports; migrate all affected callers directly, without compatibility barrels, aliases, or duplicate implementations.
- Follow strict TypeScript/NodeNext conventions, including `.js` relative import specifiers and explicit type-only imports. Keep tests colocated with their owner using `node:test` and Node assertions.
- Test observable behavior, state transitions, boundaries, and diagnostics—not import forwarding, source text, incidental wording, or wrapper choreography.
- Use real temporary files and Git repositories for filesystem/Git coverage. Substitute external agent execution and provider HTTP only at explicit dependency seams. Never use real credentials in fixtures.
- Run focused tests while developing, then the repository checks from the root:

```bash
npm run verify                     # typecheck, recursive factory tests, architecture
npm run factory -- --help          # real CLI/import smoke; no credentials or Docker needed
npm run tickets -- --help          # submission CLI/import smoke; no credentials or network
```

- For workflow/publication changes, also exercise a bounded iteration with real tickets, temporary repositories/bare remote, real logging, controlled agent results, and the relevant provider HTTP seam. Observe terminal files, pushed SHA, PR request/result, and failure settlement. Remove disposable drivers/fixtures afterward.
- For architecture-check changes, demonstrate rejection of temporary illegal imports, including a type-only deep import, then remove them. Do not weaken the checker or narrow TypeScript/test discovery to pass checks.
- For asset/harness changes, verify real preflight for both harnesses and correct handoff/MCP/model/skill resolution. Assets include the workspace-root `models.json`, `factory/infrastructure/agent-runtime/handoff-server.mjs`, `factory/infrastructure/agent-runtime/skills/`, `factory/infrastructure/sandbox/masked.env`, and `factory/infrastructure/sandbox/Dockerfile`. Pi uses `~/.pi/agent/`; oh-my-pi uses `~/.omp/agent/` with the model file mounted as `models.yml`.
- Controlled integration is not live Docker/model/provider execution. Only perform live remote writes against an authorized disposable repository; report exercised paths and unavailable external prerequisites separately.

## Documentation and repository safety

When changing the codebase, review and maintain both `README.md` and `AGENTS.md` in the same change so they stay aligned with the implementation. Update affected runtime ownership, commands, configuration, behavior, and contributor instructions; leave unaffected content unchanged. Keep historical plans historical. Do not propagate stale claims that agents create commits, that the runner performs no checkpoint commits, or that the daemon loop lives in `main.ts`.

Planning-only changes belong in `docs/plans/`. Do not add proposed-plan links, summaries, future behavior, or plan-specific instructions to `README.md`, `AGENTS.md`, or other operational documentation before implementation. Update those documents only when the corresponding behavior is implemented and verified; describe actual behavior, not intended behavior.

`docs/to-forge-tickets.md` is the user-invoked ticket-authoring skill. Keep its strict front-matter template, dependency rules, submission commands, and provider limitations aligned with the ticket parser and submission CLI. It is documentation, not an automatically installed runtime skill.

Preserve unrelated skill catalogs, samples, proof scenarios/evaluators/expected solutions, and historical runners unless the requested change requires touching them. Do not relocate or delete skill assets solely to match the runtime tree; use actual consumers to establish mount sources. Proof scenarios are independent local evaluator workflows, not live remote-publication evidence.

Proof scenarios reference the retained fixtures and tickets under `samples/v1-sandcastle/` and the runtime catalog under `factory/infrastructure/agent-runtime/skills/`. Keep those mappings aligned when their consumers' assets move; do not relocate sample or skill content as incidental cleanup.

Do not expose `.env` contents or credentials. Do not delete retained `.workspaces/`, `.logs/`, `.factory-state/` records, issue comments, or board state, and do not modify remote repositories as incidental cleanup. Preserve unrelated in-progress repository changes.
