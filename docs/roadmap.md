# Delivery Roadmap — Local Agentic Software Factory

**Status:** Proposed
**Companion to:** [Plan](./agentic-software-factory-plan.md) · [Technical Design](./technical-design.md)

## Delivery constraint

- **Jarvis is the only LLM provider.** All model traffic (factory roles and interactive Jarvis) routes through the model gateway to the Jarvis inference endpoint on the NVIDIA machine. No OpenRouter/RunPod cloud proof-of-concept phase, no Strix Halo purchase gate, and no multi-provider time-based routing. The cloud cutover and hardware evidence sections of the plan are dropped from this roadmap.
- The single-provider design simplifies the gateway (logical aliases map to one physical endpoint, with per-role aliases only) and removes the `diversity_degraded` routing case. The residual same-model review correlation risk remains; it is mitigated by fresh-context reviews and the human-gated release.

## Phases

### Phase 0 — Repository bootstrap (this repo)
- This repo becomes the source of truth for all factory-owned code and agent assets (the `platform` tree from the design; published to GitLab in Phase 1). Keep the initial layout deliberately monolithic: one orchestrator service, one launcher, one publisher, centrally versioned assets, and no queue product or generic agent-plugin framework.
- Scaffold the source layout in-repo:
  - `orchestrator/` — service skeleton with the design §7.1 modules (webhook, gitlab, projector, policy, scheduler, launcher, adapter, publisher, reconciler, reporter, release); SQLite WAL migrations with foreign keys, UTC timestamps, bounded payload references, idempotent action records, and operational runbooks.
  - `launcher/` + `publisher/` — a forced-command launcher that accepts only signed canonical run specifications and owns container lifecycle/garbage collection, plus a separate-OS-user Unix-socket publisher that validates patches against an expected base SHA and can push only `factory/*`.
  - `agent-assets/` — versioned role prompts (planner, implementer, reviewer, release-reviewer, browser-tester), bounded commands, allowlisted skills/tools, role manifests, JSON schemas (plan, implementation, review), and OpenHands/OpenCode configurations. Bundle CI validates frontmatter, schemas, relative paths, referenced assets, size limits, symlink/secret absence, and harness compilation.
  - `ci-templates/` — immutable-commit application template with contract, check, build, image, browser, and release-qualification jobs; `.factory.yaml` schema/validator rejects mutable images, path escapes, unsupported service names, and unsafe egress values.
  - `reference-app/` — a small application that exercises the repository contract, health/deployment integration, and every fixed-suite task shape. `deploy-staging/` + `deploy-production/` contain trusted pipeline code only; application repositories never contain deployment credentials.
  - `agent-images/` — pinned, scanned agent/runtime image build pipeline. The registry digest, not a tag, becomes the approved Phase 3 execution input.
- Author the initial skills, commands, prompts, schemas, and fixed task suite. The suite includes all eight plan cases, clean-checkout setup, expected evidence, seeded review defect, risk/gate assertions, concurrency procedure, evaluation rubric, scorecard, and a pinned configuration record covering model/runtime/parser/sampling, harness, assets, repository SHA, limits, and session count.

**Exit:** repository CI is green; migrations and service/launcher/publisher skeletons build; the agent-assets bundle and `.factory.yaml` validator reject malformed fixtures; the trusted CI/deployment template lints; and the complete fixed suite, scorecard, and configuration-record schemas are versioned.

### Phase 0 architecture rule — vertical slices
- Organize factory-owned behavior around capabilities, not technical layers. Each implemented capability is a small vertical slice containing its entry point, validation/contracts, orchestration logic, persistence mapping, and behavioral test where applicable.
- Keep the orchestrator as one deployable Go service, but make its internal slices explicit: webhook receipt, issue admission, reconciliation, planning dispatch, implementation dispatch, publication, review, merge qualification, and staging qualification. The existing `webhook`, `projector`, `policy`, `scheduler`, `launcher`, `adapter`, `publisher`, `reconciler`, `reporter`, and `release` packages are implementation boundaries within those slices, not independently deployed services.
- Feature-owned state remains with its owning capability/domain; shared code is limited to stateless infrastructure and pure utilities. A slice must not import another slice directly. Cross-capability access goes through a narrow public feature contract or composition-root wiring.
- Every Phase 0 plan must identify its capability boundary, public contract, behavioral verification, and later composition-root integration. Documentation-only package scaffolding MUST NOT be mistaken for implemented slices.
- Phase 0 establishes the boundaries and contracts needed for later slice delivery; it does not implement the Phase 4 workflow slices prematurely.


### Phase 1 — Foundation: GitLab core
- Deploy GitLab Self-Managed and its integrated registry on Unraid with dedicated configuration, log, and data volumes. Bind GitLab, registry, and administration surfaces to Tailscale only; make every factory project private, disable instance runners, and restrict registry visibility to project members.
- Create the `software-factory/` hierarchy:
  - `apps/` holds application repositories only. Create the orchestrator and publisher group access tokens here so inherited membership cannot reach `platform/`.
  - `platform/` holds `orchestrator`, `ci-templates`, `agent-images`, `agent-assets`, `reference-app`, `deploy-staging`, and `deploy-production`. The developer is the only human writer for the trusted CI/image/deployment projects; no implementation-agent identity is a member, the staging trigger cannot write its project, and no long-lived API bot belongs to `deploy-production`.
- Configure every enrolled application project with `main` as default, fast-forward-only merges, and `main`/`release/*` protection with push disabled for everyone and merge limited to Maintainers. Restrict `v*` tag creation to Maintainers; require successful non-skipped pipelines and resolved discussions; delete source branches after merge. The orchestrator is the only automatic merge identity; the developer retains emergency authority.
- Create group labels under `software-factory/apps`: exactly one `factory::` state (`draft`, `ready`, `queued`, `planning`, `implementing`, `ci`, `reviewing`, `fixing`, `human-review`, `blocked`, `done`), exactly one priority (default `priority::normal`), zero or more blocking gates (`gate::database`, `gate::authentication`, `gate::assumption`, `gate::manual`), and optional terminal `factory-result::{passed,failed,canceled}`. Only the developer may add `factory::ready`; the orchestrator owns later state transitions.
- Publish the ready-issue template requiring non-empty **Requirements**, **Acceptance criteria**, and **Technical constraints** sections. Support GitLab blocking links or unambiguous `Depends on` references; block discrepancies rather than guessing. A dependency is satisfied only when its issue is closed and its managed MR is merged, or the issue records that no code change was required.
- Install one signed webhook per enrolled application project for issue/work-item, merge-request, pipeline, push, note, deployment, and release events. Use HMAC-SHA256 raw-body validation with `webhook-id` and a five-minute timestamp window; use the legacy TLS secret-token mode only for an older GitLab version and rotate it after upgrade. Define developer-ID-verified `/factory retry`, `/factory cancel`, `/factory reconcile`, and `/factory approve-assumption` commands.
- Add the Free-tier policy boundary: the orchestrator stores SHA-bound independent review approval and never treats a GitLab approval icon as merge-blocking. Changes to `.gitlab-ci.yml`, included CI, `.factory.yaml`, or any repository contract script (`bootstrap`, `check`, `build`, `browser-test`) automatically add `gate::manual`.

**Exit:** the reference app is enrolled with the immutable CI template include and valid `.factory.yaml`; a signed webhook is accepted; protected branch/tag policy rejects direct push and agent publish attempts; a `factory::ready` issue validates its contract; a CI-contract change receives `gate::manual`; and neither an agent identity nor any runner can write a protected branch.

### Phase 2 — Control-plane services
- Provision the control VM with the orchestrator and LiteLLM proxy bound only to the tailnet. Configure SQLite WAL, foreign keys, `busy_timeout`, migrations-before-readiness, structured JSON logging, `/health/live`, `/health/ready`, `/metrics`, and the periodic GitLab reconciliation loop. Readiness must prove the database, current GitLab token, publisher socket, and forced-command worker are reachable.
- Provision the isolated worker VM with `factory-launcher` behind an OpenSSH forced command. Disable forwarding and PTY/shell access; expose no Docker TCP listener; grant Docker-socket access only to the launcher OS account. The launcher verifies signed, non-expired, non-replayed run IDs and labels all resources by factory instance and run ID for safe garbage collection.
- Configure LiteLLM aliases (`factory-primary`, `factory-review`, `factory-release-review`, `jarvis-coding`, `jarvis-general`) to the one version-pinned Jarvis deployment. Version-control the endpoint, model revision, runtime, context limit, tool/reasoning parser, sampling defaults, and role concurrency policy; record that revision in every run bundle. Retry model transport failures at most twice, then block as infrastructure without provider fallback or repair-cycle consumption.
- Establish network segmentation and identity boundaries: Tailscale tags for GitLab, control, worker, ordinary runners, staging, and production; deny-by-default grants; separate orchestrator, publisher, staging-trigger, registry-pull, runner, and model-sidecar credentials. Policy tests must prove agent and ordinary-runner identities cannot reach GitLab SSH, inference directly, hypervisors, Unraid administration, staging, or production.
- Create runner pools with untagged jobs disabled: non-privileged `ci-untrusted` and `browser-deterministic` pools with no protected variables; protected `deploy-staging` and `deploy-production` pools restricted to their respective trusted projects, refs, networks, and credentials. Deployment runners never execute scripts from an application checkout.
- Establish the nightly encrypted off-host backup set for GitLab data/configuration/secrets/registry, orchestrator SQLite/configuration, LiteLLM configuration/provider secret, runner inventory, and Tailscale policy. Retain 7 daily and 4 weekly generations from the first backup; record GitLab version, edition, and image digest with every generation.

**Exit:** the orchestrator readiness endpoint is green; a test model-egress sidecar reaches each logical alias while direct gateway access is denied; the launcher completes a signed create-to-destroy throwaway run and collects labeled resources; runner/tag and Tailscale-deny tests pass; and the first complete nightly backup set is off-host with every component restored once in isolation.

### Phase 3 — Agent execution boundary
- Implement the complete signed run lifecycle: resolve immutable base SHA, agent-image/assets digests, role policy, limits, services, and network policy into a canonical signed `run-spec.json`; create a credential-free checkout archive; verify all digests/signature/replay state; run as a unique non-root UID with read-only root filesystem, capability drop, `no-new-privileges`, seccomp/AppArmor, CPU/memory/PID limits, tmpfs harness home, and no host/Docker mounts.
- Create a private network for every run. Planning/review get only the model sidecar; implementation/repair may use an HTTPS proxy restricted to the repository manifest’s exact public egress hosts. Block direct outbound traffic, private/tailnet/link-local ranges, GitLab, hypervisors, deployment networks, and inference hosts. Approved ephemeral services use pinned images, synthetic credentials, health checks, and no route beyond the run network.
- The model-egress sidecar alone holds the gateway credential, permits only `/v1/chat/completions` and `/v1/models`, forces the logical model route, applies request/body limits, and annotates requests with the run ID. The agent receives only the sidecar URL and a fixed non-secret dummy value if required by a client; it cannot reach LiteLLM directly.
- Bake off OpenHands headless and OpenCode through the same process-adapter contract: canonical task/policy input; bounded JSONL events, structured result, exit classification, and workspace diff output. Select one harness from fixed-suite evidence; pin its executable/configuration and remove the losing production adapter after the decision is recorded.
- Package `agent-assets` as a read-only OCI artifact. Pin its digest in reviewed orchestrator configuration; record its source commit, content digest, selected role/command/skills, compiled-prompt hash, and adapter version in every run bundle.
- Validate returned plans, implementation results, reviews, paths, patch size, unexpected files, forbidden types, and embedded credentials. On completion/cancellation, collect sanitized bounded logs, artifacts, usage, and diff; enforce SIGTERM then SIGKILL timeout handling; remove every container, network, volume, workspace, and run directory idempotently.
- Publish only through the Unix-socket publisher: re-clone the expected base, apply without fuzz, reject submodules/tree-escaping symlinks/base mismatch, commit with factory trailers, push only the deterministic `factory/p-{project_id}-i-{issue_iid}` branch, and open/update one idempotently annotated MR.

**Exit:** a scripted plan → implement → publish run produces a credential-free run bundle and MR from an exact-base validated patch; negative probes prove signature, expiry/replay, path escape, embedded credential, direct LiteLLM access, and unauthorized egress are rejected; cleanup leaves no labeled resources; and the selected harness/configuration passes the recorded unattended-merge readiness gate before Phase 4 begins.

### Phase 4 — Orchestrator workflow
- Implement webhook receipt/deduplication, projection, reconciliation, policy, scheduling, reporting, and release modules as one service. Persist webhook deliveries, work items, dependencies, plans, runs, MRs, SHA-bound reviews, leases, transitions, idempotent actions, and release candidates in SQLite; execute GitLab mutations outside short transactions with read-before-retry checks.
- Reconcile at startup and at least every 60 seconds against factory-labelled issues, managed MRs, pipelines/SHAs/discussions, releases/environments/deployments, and launcher-labelled resources. GitLab wins projection disagreements except an unexpired active lease; a lost database drains dispatch, rebuilds from GitLab, and requires a human decision only for captured-but-unpublished patches.
- Schedule valid ready/queued issues by satisfied dependencies, priority, creation order, project, and IID. Hold at most two implementation leases; dispatch planning first; normalize and lease only material migration/auth/bootstrap/route/contract conflicts in lexical order; retain the work/conflict lease through terminal state; release implementation capacity while CI runs; reserve the third slot for review and recovery.
- Enforce the state machine and repair accounting. Infrastructure faults retry twice without consuming a cycle; deterministic code, CI, browser, conflict, or reviewer failures consume one of three combined repair cycles. Escalate early for repeated findings, changed criteria, material scope expansion, emerging database/authentication risk, nondeterministic tests, unverifiable behavior, or contract disagreement.
- Publish plans, run bundles, structured reviews, labels, and idempotent GitLab notes. A reviewer uses fresh context and no implementation transcript; approval is valid only for the reviewed source SHA and invalidates on every push. Human labels/comments control retry, cancel, reconciliation, and assumption approval.
- Apply the atomic merge predicate immediately before a SHA-parameterized merge: eligible issue/dependencies, open non-draft MR to `main`, matching valid review SHA, successful pipeline for that SHA, resolved discussions, mergeability, no gates, repair count within limit, and human approval for CI/manifest trust-file changes. Wait for staging health of the emitted digest before closing the issue.

**Exit:** two non-conflicting reference-app tickets complete unattended through `ready → planning → implementing → CI → reviewing → merge → staging → done`; recovery and review share the reserved slot without starving either implementation; risk/assumption/CI-contract tickets stop at human review; reconciliation recovers an injected webhook loss; and negative merge cases prove no stale-SHA, failed-CI, unresolved-discussion, incomplete-dependency, conflict, or pending-gate MR can merge.

### Phase 5 — Release and production
- Implement release qualification only from a protected `release/<version>` branch whose tip already has a successful `main` pipeline and immutable manifest. Resolve the existing digest without rebuilding; serialize the shared test environment with the project release/staging resource group; deploy through the trusted staging project; and record the exact observed digest.
- Run repository checks, release-specific verification, deterministic Chromium Playwright, deep fresh-context review from the prior production release, and one bounded exploratory browser session against that exact deployment. Start with one worker, controlled test data/locale/timezone/viewport, clean contexts, and one retry only for trace capture; pass-on-retry is flaky and blocks pending human classification. Retain JUnit, HTML, failure screenshots/video, trace, console errors, and failed network requests.
- The exploratory browser receives only release criteria, test URL, and a pre-authenticated disposable synthetic account. It is restricted to the test origin/fixture broker and returns reproducible actions, expected/observed behavior, screenshot/trace, console/network evidence, severity, and confidence. The developer classifies every finding as release blocker, follow-up, expected, or not reproducible.
- Publish one idempotent GitLab release report containing candidate and prior production commit/digest, all gate outcomes/evidence, harness/model revisions, environment URL, and timestamps. Any staging digest change makes qualification stale and requires a full rerun; unclassified exploratory findings keep production promotion unavailable.
- Production is a human-started job in the separate private production project. It revalidates the release tag, commit, digest, and green qualification report; deploys `image@sha256` without rebuilding; records the environment deployment; and stores prior/new digest, deployment IDs, commit/tag, time, schema note, and operator for rollback. A rollback job accepts only a previous successful deployment ID; non-backward-compatible migrations require `gate::database` and a human rollback procedure.

**Exit:** one release completes qualification from an existing immutable digest; staging-digest mutation invalidates and reruns qualification; all exploratory findings are classified; the human promotes the exact qualified digest; and a rollback drill redeploys the recorded prior digest without using a mutable tag.

### Phase 6 — Hardening and operations
- Exercise and document the failure-recovery table: duplicate/out-of-order or missing webhook, orchestrator restart, worker disappearance, model/gateway outage, GitLab outage/rate limiting, patch-base change, CI/review failure, staging failure, production failure, SQLite loss, and token expiry. Prove bounded infrastructure retries, no silent provider substitution, no unsafe blind GitLab-write retry, and correct blocked/escalated ownership state.
- Run token-expiry checks and open/update the GitLab incident issue at least 30 days before expiry; rotate quarterly and immediately after suspected exposure. Emit bounded JSON logs and low-cardinality metrics for webhook lag, reconciliation, queue/leases, runs/repairs, GitLab/model/publish/deployment activity, release gates, and backup age. GitLab remains the notification surface; document local log/health-only behavior during GitLab outage.
- Run the quarterly isolated restore drill using the exact recorded GitLab version/edition: restore GitLab/configuration/secrets/registry, restore the orchestrator with outbound writes disabled, dry-reconcile against restored state, re-register runners, rotate restored credentials, exercise a reference issue through staging, and prove production remains inaccessible. Record recovery time and data age against the ≤24-hour RPO and one-working-day restore objectives.
- Use benchmark and operational evidence to decide the remaining design §17 choices: Docker hardening versus stronger per-run isolation, egress cache/allowlist, Playwright matrix, LiteLLM virtual-key database, and registry backup method/retention. Do not add complexity absent measured need.

**Exit:** the failure-recovery exercises meet their bounded retry/blocking rules; the quarterly restore drill meets the V1 RPO/RTO objectives; token/backup/release operational signals produce GitLab incidents; the egress allowlist is minimized from observed need; and the factory sustains WIP 2 plus the reserved review slot against Jarvis without unrecorded intervention.

## Open decisions (this roadmap only)

| Decision | Resolution path |
|---|---|
| Jarvis model, serving config, context/quantization | Frozen benchmark on the fixed task suite before Phase 4 enables unattended merge; results recorded in GitLab |
| Harness: OpenHands vs OpenCode | Bake off on the same fixed suite in Phase 3; pick by completion quality and structured-output validity |
| Per-run isolation | Start with the specified Docker boundary; move to microVMs only if evidence justifies the added complexity |
| Egress host allowlist/cache | Derived from the fixed task suite during Phase 3 |
| Playwright sharding/extra browsers | Only after measured suite duration justifies it |
| LiteLLM virtual-key database | Retain trusted-sidecar credentials without PostgreSQL unless measured operations show material budget or revocation benefit |
| Registry backup method/retention | Start with filesystem backup and Phase 2’s retention target; add object-storage replication only when registry size or backup window requires it |

## Risks

- **Single-provider concentration:** any Jarvis/NVIDIA outage stops all factory work; active runs get bounded retry, then block. Mitigation: gateway health checks, restart runbook, and keeping the provider configuration change (adding a second endpoint) to a gateway commit, not an orchestrator change.
- **Same-model review correlation:** one model reviews its own work in fresh context; deterministic CI and the human-gated release remain the backstops.
- **Prompt injection / credential exfiltration:** unchanged from the design — no credentials in agent containers, deny-by-default network, sidecar-brokered model access.
